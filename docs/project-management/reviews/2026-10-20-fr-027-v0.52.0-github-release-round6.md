## 2. 正確性與回歸

- 判定：部分通過。
- 證據：本輪 source diff 僅調整 Windows workflow；未改產品 runtime。`.github/workflows/windows-preview.yml:21-38` 在 checkout 前執行 global `core.autocrlf=false`，對 `actions/checkout@v5` 注入 `GIT_CONFIG_COUNT` override，並於安裝／封裝前檢查有效值確為 `false`。Repo tree 沒有 `.gitattributes`；本機只讀環境 override probe 亦回傳 `false`。
- 換行設定判斷：這是針對已觀察到 checkout CRLF 轉換的有效修正。Git 官方文件說明 `GIT_CONFIG_COUNT` pairs 會覆寫設定檔值；`actions/checkout@v5` 的 Git command manager 將 action process environment 傳給子 Git 程序，因此 checkout step 的 override 會生效。`core.autocrlf=true` 會在 checkout 將 LF 轉為 CRLF。參考：[actions/checkout v5 Git command manager](https://github.com/actions/checkout/blob/v5/src/git-command-manager.ts)、[Git config：GIT_CONFIG_COUNT](https://git-scm.com/docs/git-config/2.51.1#Documentation/git-config.txt-GITCONFIGCOUNT)、[Git config：core.autocrlf](https://git-scm.com/docs/git-config/2.51.1#Documentation/git-config.txt-coreautocrlf)。
- 限制：此設定支持「checkout 會保留 repo 中的 LF」這個靜態判斷，但不能單獨證明後續 runtime 準備、測試與 electron-builder 封裝後的每個 packaged byte 仍是 LF／與 macOS 相同。repo 未提交 `.gitattributes`，降低了 repo 內 eol 規則介入的可能；仍須取得同 SHA Windows artifact，驗證 manifest checksum 並逐檔比對 73 個共用 packaged app hashes。Workflow 產生 manifest，但只有 artifact 核驗才能證明實際封裝結果。故 `core.autocrlf=false` 足以修正已知 checkout 成因，不足以解除端到端封裝 gate。
